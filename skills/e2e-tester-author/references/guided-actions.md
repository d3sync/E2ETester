# Guided Actions (package schema 1.6)

Use optional top-level `guidedActions` for manual recovery or administrative actions outside the sequential `cases` flow. Each entry uses the existing case object shape: unique id, title, instructions, request and assertions. IDs must be unique across actions and cases. No automatic execution, fixtures, database checks, variations or Swagger steps are supported here. A maximum of 100 actions is allowed, with at most 1000 cases and actions combined.

An entry without preparation sends its HTTP request only after the tester reviews the resolved request and confirms it. It is recorded as a separate Guided Action run in Saved runs, with the source run ID in its description; it does not change source case verdicts or coverage. Use `{{case.create-id./token}}` to target the exact response from a selected saved run. Cleanup defaults to the latest complete HTTP 2xx response for each referenced case, even if a later duplicate attempt or another assertion failed. The attempt picker allows choosing a specific complete response regardless of verdict. Normal test-flow bindings remain strict. A missing, previously redacted or interrupted response cannot resolve; ask the tester to look up and enter the verified resource ID. Never infer it or delete broad sets of records. Existing create cases remain unchanged; actions do not make creation idempotent.

An entry with preparation applies only its PreparationPlan, not its request. request.identityRef selects the affected test identity; API capture/update identities remain in the plan. The tester can edit the plan and choose flags in the existing confirmation dialog. Original values are persisted before writes. An applied action is scoped to the current package, environment and run, not an individual case; pending/uncertain operations block normal test sends. Explicit HTTP Guided Actions remain available for repair with the selected identity, independently of test preparation guards; recovery records are retained. Fresh JWT/claim requirements still apply. Case preparation, another permission action, Finish and explicit Restore use the existing restoration workflow. After restart, resume the original run or restore its pending changes before starting another run. Restore refuses conflicting external changes.

The always-available Restore button restores captured originals. A chosen permission preset is a temporary change, not an arbitrary overwrite of a recovery record. If the captured original is unavailable, provide a verified target account and explicitly chosen permission value; never assume an all-permissions value.

MCP can validate/store/export schema 1.6 packages. Guided Action execution is currently desktop-only; do not use prepare_case with an action ID or imply that a package definition grants MCP mutation permissions. Existing case preparation tools keep their host approval requirements. Reports containing schema 1.6 packages use report schema 1.9.

Desktop Run anyway: testers can opt in for one request to bypass prior-case pass requirements, including setup/remote-IP coverage. Available earlier complete responses can supply bindings even when later attempts failed. Missing values must be entered manually; assertion outcomes and previous history are not rewritten. The override is recorded in attempt changes as execution.prerequisites. It does not apply preparation mutations or disable restoration safeguards. MCP remains strict by default; do not weaken generated expectations to work around a failed prerequisite.

Resource lookup: cleanup candidates must supply every requested JSON pointer for their source case, not merely have HTTP 2xx status. Plain-text duplicate errors are not resource IDs. Find saved resource searches up to 1000 recent runs in the same workspace/package/API environment and selects a run for review without sending a request. If no response contains the ID, use a verified lookup and manual input; do not convert an error body to a token.

## Captured values (0.7.20 and later)

The application no longer redacts request/response values, headers, cookies, fixture cells, assertions, preparations, drafts, packages or reports, including MCP results. `sensitive`, `bodySensitive` and `sensitiveColumns` remain accepted for older packages but have no masking effect. Use actual captured `token`/`groupToken` values for bindings and comparisons. There is no redaction setting. Older saved `[REDACTED]` values cannot be recovered: obtain a fresh response or a verified manual resource ID. Continue authoring reusable templates with identity/connection aliases rather than embedding credentials.

## Named permission identities and missing source values (0.7.22)

Use stable named identities for distinct permission sets: `cloud-user` for normal/full-access tests, `cloud-clientadmin` for ClientAdmin, and separate descriptive aliases for other exact flag combinations (for example `cloud-clientadmin-telephony`). Reuse the same alias for every case with that permission set, even when all roles belong to one database account. Never flatten role aliases to cloud-user or generate timestamp identities. A valid JWT whose configured claim equals the required value satisfies permission preparation across cases, suites and restarts. Prepare and sign in only when that role token is unavailable, expired or mismatched. Restoring the database does not invalidate already-issued JWTs. Ordinary non-permission data preparation remains scoped to its operation. Named identities persist in protected AppData storage across workspaces for the same API origin; JWT exp controls retention, with a fixed 24-hour fallback for bearer tokens without exp. API tokens are retained until removed. Decoded expiry is not authentication validation.

Run anyway bypasses prior-case pass requirements. When a response binding has no usable value, the desktop prompts for the verified value and records it with the request override. It never invents a resource ID or automatically reruns the create case. Missing values can be cancelled without sending.

## Required convenience actions (0.8.2)

Always include a basic Guided Action to repeat the suite's known access check outside coverage. For permission suites include Set permissions for every required role and a `Choose permissions…` action with the same target and complete known flags. Its instructions must explain that the user can enter a numeric value or select flags, then explicitly apply; entering the value synchronizes checkboxes. Explicit Guided Actions apply and verify the database change even if a saved role JWT already matches. Normal cases still reuse valid matching JWTs. Restore through built-in Restore changes, never a fixed-value restore action. Include cleanup for created resources when a verified cleanup endpoint exists. If the permission/cleanup contract is missing, ask for it; do not invent a mutation. No new schema fields are needed for manual selection: use an ordinary preparation action.
